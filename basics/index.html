    기본 용어와 범위¶

    비개발자 청중이 본 시리즈를 시작하기 전에 알아두면 좋은 기본 용어와, 본 시리즈가 다루지 않는 영역(범위 밖 안내)을 짧게 정리합니다. 본격적인 문법·내부 구조 학습이 아니라, 단어가 등장했을 때 멈추지 않을 정도가 목표입니다.

    챗봇 vs 에이전트 — 「물어보기」 vs 「맡기기」¶

    생성형 AI 제품은 사용 방식으로 두 갈래로 나눠 볼 수 있습니다. 챗봇·에이전트가 각각 무엇인지는 이 절에서 정하며, 다른 페이지에서 두 단어가 나오면 모두 여기 정의를 가리킵니다. 본 교육의 3단계 모델과도 직접 연결됩니다.

    챗봇 — 물어보기

    사람이 묻고 AI가 답합니다. 결과를 받은 뒤 실제 처리는 사람이 직접 합니다.

    적합: 정보 수집, 아이디어 브레인스토밍, 초안 다듬기

    본 교육: 1단계 (참가 전제 — 이미 경험)

    에이전트 — 맡기기

    AI가 직접 파일을 열고 작업을 수행합니다. 사람은 목표만 정해 주고 결과를 검토합니다.

    적합: 반복 작업, 여러 단계 자동화, 로컬 파일 처리

    본 교육: 3단계 — Claude Cowork 실습 (Code는 보조 도구)

    왜 이 분류가 중요한가요?

    챗봇(물어보기)과 에이전트(맡기기)는 반복 작업에서의 비용 구조가 다릅니다. 같은 일을 매번 새로 시킬지, 한 번 맡길 수 있게 만들어 둘지가 갈리죠.

    본 교육은 챗봇과 에이전트 사이에 2단계(프롬프트 재활용) 를 다리로 두어, 챗봇 사용자에서 에이전트 활용자로 자연스럽게 옮겨가도록 설계되어 있습니다. 그 비용 차이와 단계별 위치는 3단계 모델에서 자세히 다룹니다.

    에이전트 = 모델 + 하네스¶

    바로 위 챗봇 vs 에이전트에서 에이전트를 "AI가 직접 파일을 열고 일하고, 사람은 목표만 주고 결과를 검토하는 사용 방식"으로 봤습니다. 그럼 그 에이전트는 무엇으로 이뤄져 있을까요? 딱 두 부분입니다.

    에이전트 = 모델 + 하네스

    • 모델 — 생각하는 머리. 똑똑하지만 틀릴 수 있고, 매번 답이 조금씩 다를 수 있는 부분입니다 (→ 아래 세 형태의 비결정성과 같은 성격). 만드는 회사는 여럿입니다 (Anthropic·OpenAI·Google 등). 본 강의 실습은 Claude입니다.
    • 하네스(harness) — 그 머리를 둘러싼 작업 구조, 쉽게 말해 사람이 짜 둔 틀입니다. 어떤 도구·자료를 쓸지, 어떤 순서로 일할지, 결과를 어디서 확인할지가 모두 여기 들어갑니다.

    모델에게 건네는 말 한마디(프롬프트)는 하네스가 아닙니다. 머리에게 질문을 하나 던지는 것이죠. 같은 지시를 저장해 반복하려고 묶어 두면(스킬) 그때부터 하네스의 부품이 됩니다 (→ 아래 세 형태의 1회성 프롬프트 vs 에이전트 스킬 경계와 같은 선).

    하네스는 결국 "내가 세팅하는 것들"¶

    하네스를 펼쳐 보면 대부분 이미 있는 걸 고르고·연결하고·정하는 일입니다. 출처가 셋이고, 그중 새로 만드는 내 몫은 얇습니다.

    내가 만드는·정하는 것 (얇다)

    전부 이 강의가 이미 언급하고 있는 것들입니다.

    • 지시를 정리해 저장 — 매번 길게 쓰던 부탁을 한 번 다듬어 스킬로 (→ 세 형태)
    • 자료를 붙이기 — 어떤 폴더·문서를 보여줄지 (→ 메타 원칙 ④)
    • 순서를 정하기 — "계획부터 받고 → 검토 → 실행" (→ 메타 원칙 ①)
    • 확인 단계를 두기 — 결과를 어디서 직접 읽고 점검할지 (→ 메타 원칙 ③)

    고르고·연결만 하는 것 (안 만듦)

    이미 만들어진 것을 고르고 연결하기만 합니다.

    • 제품·모델 고르기 — claude.ai / Cowork / Code, 그리고 모델(Fable·Opus·Sonnet·Haiku) 중 무엇을 쓸지 (→ 기능 비교표)
    • 외부 서비스 연결 — 이미 있는 GitHub·Slack 같은 서비스에 로그인·승인해 연결합니다 (→ 외부 컨텍스트). 직접 만드는 게 아닙니다.

    그럼 "알아서 파일을 열고 명령을 실행"하는 그 큰 부분은요? 그건 에이전트 제품을 만든 회사가 설계한 구조입니다. 격리된 환경에서 도구를 정해진 순서로 불러 쓰는 틀이죠 (Cowork의 보호 모델의 격리 VM·송신 정책이 그 실물). 모델이 스스로 자율적인 게 아니라, 회사가 만든 하네스가 모델을 굴린 것입니다.

    이 목록은 전부 사람이 고르고·연결하고·정해 둔 것들입니다. 내 몫은 고르고·연결하고·정하고·확인하는 조립이고, 회사 몫도 정교하게 설계된 구조죠. 그래서 결과 품질은 누가 똑똑하냐가 아니라 조립을 잘했는가 + 사람이 검토했는가에서 옵니다.

    흔한 오해 — 「에이전트끼리 알아서 회의하면 좋은 결론이 나온다」

    AI 여러 개를 띄워 서로 회의시키면, 사람 손을 떠나 알아서 조사하고 정답을 내놓을 거라 기대하기 쉽습니다. 그렇지 않습니다.

    • 틀(하네스)은 누군가 설계해 둔 것입니다. 무엇을 시킬지·어떤 자료를 줄지·어떤 순서로 할지를 정한 건 제품을 만든 회사, 그리고 그 위에 설정한 나죠.
    • 모델은 똑똑해도 틀릴 수 있습니다. 여러 AI가 모여 회의해도, 잘못된 전제 위에서는 그럴듯하게 함께 틀린 결론을 낼 수 있습니다.
    • 좋은 결론은 「알아서」 나오지 않습니다. 틀을 잘 짠 사람과 결과를 검토한 사람이 만듭니다.

    그래서 AI 결과물 검토·이해 의무는 협상 대상이 아닙니다.

    물론 멀티 에이전트가 쓸모없다는 뜻은 아닙니다. 사람이 역할을 나눠 주고(예: 하나는 근거를, 하나는 표현을 점검), 각자에게 명확한 기준표를 주고, 결과를 사람이 검토하면 분명히 유용합니다. 가치를 만드는 건 자율이 아니라 잘 나눈 역할 + 명시적 기준 + 사람의 검토입니다. 그리고 이 핵심은 단일 에이전트로도 "기준을 하나씩 짚어 가며 점검"해 대부분 얻을 수 있습니다. 멀티 에이전트는 그 그림을 더 또렷이 보여줄 뿐입니다.

    결과물의 성격 — 1회성 프롬프트 · 에이전트 스킬 · 애플리케이션¶

    AI 활용 3단계와는 다른 컷입니다

    이름이 닮아 헷갈리기 쉽지만, 보는 기준이 다릅니다.

    • AI 활용 3단계 = 내가 올라가는 학습 단계(챗봇 사용 → 프롬프트 재활용 → 에이전트 활용). 끝은 본 교육의 도착점인 에이전트입니다.
    • 결과물의 세 형태(이 절) = 만들어 둔 결과물의 성격(결정성·비용 기준). 끝은 본 교육 경계 밖인 애플리케이션입니다.

    그래서 앞 두 칸은 거의 겹치고, 마지막 칸만 갈립니다:

    • ① 챗봇 사용 ≈ 1회성 프롬프트
    • ②·③ 프롬프트 재활용·에이전트 활용 ≈ 에이전트 스킬 (본 교육)
    • 그 너머 = 애플리케이션 — 결정적 코드 소프트웨어. 본 교육이 다루는 범위 밖입니다(이 강의는 에이전트 스킬까지).

    생성형 AI는 기본적으로 비결정적입니다

    동일한 지시를 입력해도 매번 답이 조금씩 다를 수 있습니다. AI를 어떤 형태로 활용하느냐에 따라 이 비결정성을 얼마나 통제할 수 있는지가 달라집니다.

    결과물을 만드는 방식은 그 성격에 따라 셋으로 나뉩니다. 같은 작업도 어떤 형태로 만드느냐에 따라 결과의 일관성과 만드는 비용이 크게 달라집니다.

    축 1회성 프롬프트 에이전트 스킬 (본 교육) 애플리케이션 (소프트웨어)
    무엇인가 챗봇에 그때그때 입력하는 한 번짜리 지시 자주 쓰는 프롬프트·절차를 재사용 가능한 형태로 묶어둔 자산 코드로 작성된 프로그램
    결정성 비결정 비결정 (내부가 LLM 호출) 결정
    결과 일관성 매번 결과가 조금씩 다를 수 있음 동일한 형식·접근 보장 (값은 다를 수 있음) 동일 입력 → 동일 출력
    만드는 비용·누가 없음 — 누구나 즉시 낮음 — 비개발자도 직접 만듦 큼 — 설계·코드·테스트가 필요 (엔지니어링 영역)
    언제 적합한가 일회성·탐색·맥락이 매번 다른 작업 반복되는 동일 패턴 작업 대규모·다수 사용자·결정적 신뢰성이 핵심인 작업

    본 교육이 강조하는 에이전트 스킬은 두 끝점 사이에 있습니다. 비개발자가 만들 수 있는 비용이면서, 반복 작업의 일관성을 크게 끌어올립니다.

    반대편 끝의 애플리케이션(결정적 코드 소프트웨어)은 같은 '앱'이라도 결이 둘로 갈립니다.

    • 나 혼자 쓰는 개인용 앱(작은 도구·프로그램) — 요즘은 에이전트가 코드 작성까지 거들어, 관심이 있다면 충분히 도전해 볼 만한 다음 발걸음입니다.
    • 공식 시스템·다수 사용자용 앱 — 결정적 신뢰성이 핵심이라 설계·테스트·유지보수 같은 엔지니어링이 여전히 많이 듭니다.

    어느 쪽이든 본 교육이 다루는 범위는 아닙니다 — 초점은 비개발자가 직접 만드는 에이전트 스킬입니다. 그리고 개인용이라도 앱으로 갈수록 읽고 이해하고 검토하는 책임은 함께 무거워집니다.

    마크다운¶

    마크다운(Markdown)

    텍스트만으로 서식(제목·목록·강조·표)을 표현하는 가벼운 문서 형식입니다. 파일 확장자는 .md이며, AI가 가장 잘 다루는 출력 포맷 중 하나입니다.

    한 줄 예시 — # 제목 → 큰 제목, **굵게** → 굵게, - 항목 → 글머리표.

    본 강의는 마크다운 문법 학습은 하지 않습니다. 단어가 나왔을 때 멈추지 않을 정도면 충분합니다.

    본 시리즈에서 마크다운은 메타 원칙 ② "데이터와 뷰의 분리"의 뷰의 예시로 등장하고, 실습 시리즈의 step04-wrong-answer-note에서는 자녀용 학습 리포트의 출력 포맷으로 쓰입니다.

    외부 컨텍스트¶

    외부 컨텍스트 — MCP·RAG라는 용어를 들으셨다면

    내가 가진 자료(사내 문서·웹·DB 등)를 AI에 붙여 답하게 하는 일반 개념을 외부 컨텍스트라고 부릅니다. 한 대화 안에 직접 첨부하는 자료는 메타 원칙 ④ "컨텍스트(대화방) 관리"에서 다루고, 외부 자료원을 표준 방식으로 연결하는 것이 그 너머입니다.

    • MCP (Model Context Protocol) — 외부 자료원을 AI 클라이언트에 표준 방식으로 연결하는 프로토콜입니다. "어떻게 연결하느냐" 에 해당합니다.
    • RAG (Retrieval-Augmented Generation) — 관련 조각을 검색해 컨텍스트에 끼워 넣어 답을 만드는 흐름입니다. "무엇을 하느냐" 에 해당하며, MCP와는 층이 다릅니다.

    실제로 연결하는 방법은 2부 — 도구·데이터 연결에서 다룹니다. 1부는 Claude 단독 사용을 기본으로 하니 여기서는 두 단어의 뜻만 알아두면 충분합니다. 커넥터로 연결하는 절차와 MCP 서버를 고르고 등록하는 방법은 2부에서 화면 기준으로 안내합니다.

    단, RAG의 내부 구조·구현 패턴은 2부에서도 다루지 않습니다. 개발자 영역이기 때문입니다. 이런 흐름이 있다는 신호로 알아두면 됩니다.
