# Issue #42 의사결정 — 엔지니어링 3분과 비교 대신 '모델 + 하네스' 멘탈모델

> 이 문서는 이슈 #42의 방향을 정한 근거를 남긴다. 본 framing이 콘텐츠로 안착하면 이슈 완료 시 ADR 승격 후보.

## 맥락 (Context)

- 본 강의는 **비개발자 대상 Claude '실습' 강의**다. 이론 파트를 재구성하면서 AI 자동화·에이전트 개념을 어떻게 가르칠지 결정이 필요했다.
- 해소하려는 오해: **"하네스를 구축해 멀티 에이전트를 띄우면, 에이전트끼리 알아서 회의·조사해서 좋은 결론이 창발한다"** 는 시선. 이슈 #42는 이 오해를 풀기 위해 구상되었다.

## 검토한 선택지

| 선택지 | 내용 | 판정 |
|--------|------|------|
| A | 프롬프트/컨텍스트/하네스 **'엔지니어링' 3분과**를 나란히 비교 강의 | ❌ 기각 |
| B | **"그냥 자동화"** 개념만 전달 | ❌ 기각 |
| C | **`에이전트 = 모델 + 하네스`** 멘탈모델 하나로, 하네스=사람이 짜는 틀임을 드러내 오해 해소 | ✅ 채택 |

**A를 기각한 이유**: 용어 3개는 인지 부하가 크고 모두 개발자 실무 프레이밍이며, ADR-0005의 메커니즘 결과형 우회 원칙과 충돌한다. 무엇보다 "하네스 엔지니어링"을 정교한 분과로 명명하면 *"대단한 기술이 뒤에서 돈다"* 는 인상을 주어 깨려는 오해를 오히려 **강화**한다(역효과).

**B를 기각한 이유**: 오해의 정체가 '자동화 = 자율 지능' 착각이다. 자동화만 말하면 *set & forget* 로 더 굳어져 오해를 못 푼다.

## 결정 (Decision)

- 이론 파트에서 **엔지니어링 3분과 비교는 하지 않는다.**
- **`에이전트 = 모델 + 하네스`** 구도만 쉬운 말로 전달한다:
  - **모델** = 똑똑하지만 틀릴 수 있고 매번 달라지는(비결정적) *생각하는 부분*
  - **하네스** = 그 둘레에 **사람이 직접 세팅하는 것들** (지시·붙여준 자료·단계·내 검토)
- **핵심 메시지**: 좋은 결과는 에이전트가 알아서 회의해서 *창발*하는 게 아니라, **구조를 짠 사람 + 검토한 사람**이 만든다.
- **용어 운용**:
  - '프롬프트'는 실습 전체가 이미 다루고, '컨텍스트'는 `docs/basics.md` §외부 컨텍스트로 이미 깔려 있다 → 별도 분과로 격상하지 않는다.
  - '하네스'는 브리지 용어로 **1회만** 노출하거나, 본문에선 *"모델 + 내가 짜주는 틀"* 우리말로 풀어도 된다(단어 노출 여부는 docs 작성 단계 디테일).
- 하네스 **'범위'** 는 비개발자 기준 **"내가 세팅하는 것들"** 로 구체·작게 잡는다 → 그 작음 자체가 '마법 아님'의 증거다.
- 외부 자료(Martin Fowler *harness-engineering*)는 개발자용(테스트·타입·CI) 범위라 docs 본문에 직접 인용하지 않고, **원칙만** plan 근거로 빌려온다.

## 정합성

- **ADR-0001** — 에이전트 정의·AI 활용 3단계 모델과 정합("에이전트 = 모델 + 하네스" 기준).
- **ADR-0005** — 메커니즘을 결과형으로 우회하는 본질 메시지 프레임 계승.
- **ADR-0008** — 비결정성·세 형태(1회성 프롬프트·에이전트 스킬·애플리케이션) 분류와 인접, 충돌 없음.
- **실습 원칙 ②(결과물 검토 의무)** — 이 오해 해소 메시지가 안착하는 자리.
