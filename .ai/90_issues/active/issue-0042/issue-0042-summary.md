### Task 1: '모델 + 하네스' 멘탈모델 + 오해 해소 정립

- **결과**: 완료
- **수행 내용 요약**:
  - `에이전트 = 모델(생각하는 머리) + 하네스(사람이 짜 둔 틀)` 한 줄 멘탈모델과 비개발자 한 줄 정의·대비표 정립.
  - 멀티 에이전트 자율성 오해 해소 "3박자"(하네스는 마법 아님 / 모델은 틀릴 수 있음 / 좋은 결론은 알아서 안 남)와 docs용 "흔한 오해" 박스 초안 작성. 프롬프트↔하네스 경계("말 한마디" vs "둘러싼 구조") 명시.
  - 작업 파일은 정리됨 — 결론은 `docs/basics.md` §에이전트 = 모델 + 하네스에 반영(상세 도출 과정은 git 이력).
- **특이 사항**:
  - 핵심 발견 — 강의가 이미 하네스 구성요소를 다 가르침(§에이전틱 엔지니어링, 메타 원칙 ①③④). Task 1은 새 개념 도입이 아니라 조각을 한 구도로 묶는 일.
  - 정합성 확인: ADR-0001(해부 축 ≠ 학습자 수준 축, 강제 매핑 안 함), ADR-0005§3/ADR-0008('비결정' 단어 새 자리 도입 안 함, 결과형 유지)와 충돌 없음.
  - 사용자 교정(2회) 반영: 하네스 출처는 **셋**(회사가 만든 제품·모델 / 외부 서비스·사내 인프라는 내가 *연결만* / 내가 만드는 설정). "누가 만드나=내가"는 과단순화 — 대부분 *이미 있는 걸 조립·연결*. MCP로 GitHub·Slack·Jira·Confluence 잇는 건 만드는 게 아니라 연결. '알아서 한 동작'의 정체 = 회사가 만든 하네스가 모델을 굴린 것 → 자율성 오해를 더 강하게 해소. (메타포 '켜/층'은 비개발자 톤상 제거)
  - 모델 제공자는 여럿(Anthropic·OpenAI·Google +오픈소스)으로 소개 — 이론/1단계 예시 언급, 실습은 Claude (ADR-0001·intro §products 정합).
  - 멀티 에이전트 *긍정* 사례 추가(기획안 분야별 기준 검수: 법무·재무·보안 + 평가 기준표) — '오해' 박스의 건설적 짝. 교훈: 가치는 자율이 아니라 *역할 분업 + 명시적 기준 + 사람 검토*(메타 원칙 ①③). 개념 사례이며 단일 에이전트로도 핵심 획득 가능 → docs 배치는 Task 3.

### Task 2: 하네스 범위를 "내가 세팅하는 것들"로 구체화

- **결과**: 완료
- **수행 내용 요약**:
  - "내가 하는 일"을 **만들기**(지시 저장=스킬 / 자료 붙이기 / 순서 정하기 / 확인 단계 / 합격 기준)와 **연결하기**(제품·모델 고르기 / 외부 서비스 잇기 — 안 만들고 연결만)로 2열 분류.
  - 만들기 항목 전부를 강의의 메타 원칙 ①③④·basics 세 형태에 매핑 — 새 개념이 아니라 *이미 가르친 것을 하네스로 묶음*임을 명시.
  - 회사가 만든 부분(제품·모델·격리 VM·송신 정책)도 *자율 지능이 아니라 설계된 구조*임을 함께 짚어 → 세 출처 어디에도 "비밀스러운 AI 두뇌 없음"으로 수렴.
  - 작업 파일은 정리됨 — 결론은 `docs/basics.md` §하네스는 마법이 아니라 "내가 세팅하는 것들"에 반영(상세는 git 이력).
- **특이 사항**:
  - 핵심 프레임 — *목록이 짧고 익숙하다는 사실 자체가 "마법 아님"의 증거*. 결과 품질은 「누가 똑똑하냐」가 아니라 「조립을 잘했는가 + 사람이 검토했는가」로 수렴(Task 1 3박자와 동일 결론).
  - 표현 방식 제안 5종 정리(2열 대비·짧은 체크리스트·내부 용어 자연어 변환·격상 회피·오류 가능성형) — 확정은 Task 3·4.
  - 정합성: basics §에이전틱·§외부 컨텍스트, intro §products·기능 비교표·§Cowork 보호 모델, ADR-0001, 메타 원칙 ①③④ 모두 충돌 없음(Task 1 §4 + Task 2 관점 재확인).
  - 현행 docs(`intro.md` 기능 비교표·§Cowork 보호 모델, `basics.md` §에이전틱·§외부 컨텍스트, `index.md` 메타 원칙 ①③④, ADR-0001, `glossary.md`) 직접 대조 검증 완료 — 분류안과 충돌 없음. 본문 반영 시 최종 확인은 Task 4에서 1회 더.

##### S5 후속 — 「3단계 ↔ 세 형태」 삼분할 충돌 해소 (점검 피드백 2)

- **계기**: 사용자가 홈 "AI 활용 3단계"와 기본용어 "AI 활용의 세 형태"가 **이름·형태가 닮고 앞 두 칸은 같은데 마지막 칸만 달라**(3단계 끝=에이전트 vs 세형태 끝=애플리케이션) 수강생이 혼란스럽겠다고 지적.
- **결정 (옵션 1 — 다리 놓기 + 개명)**: 둘 다 유지(세형태는 ADR-0008 분류라 보존). "단계가 아니라 **결과물 성격(결정성·비용) 컷**"임을 대놓고 드러냄.
- **반영 내용**:
  - `basics.md`: 세형태 제목 "AI 활용의 세 형태" → **"결과물의 성격 — 1회성 프롬프트 · 에이전트 스킬 · 애플리케이션"**(3단계와 이름 echo 제거, 앵커 `#three-forms` 유지). 표 **앞**에 `!!! note "3단계와는 다른 컷"` 신설 — 두 컷 정의 + 매핑 다리(① 챗봇≈1회성 / ②·③ 재활용·에이전트≈에이전트 스킬 / 그 너머=애플리케이션·범위밖). 표 뒤 옛 각주 인용구 제거(앞 다리로 대체). 본문 "AI를 활용하는 방식" → "결과물을 만드는 방식 … 성격에 따라"로 축 명시.

##### S5 후속 2 — 애플리케이션 "범위 밖" 표현 정정 (점검 피드백 3)

- **계기**: 사용자가 "애플리케이션 = **개발자가 만드는**"은 부정확 — 에이전트(에이전틱 코딩)가 앱을 만들 수 있다고 지적. "범위 밖"의 의미(=강의가 거기까지 안 다룸) 확인 요청.
- **확인**: "범위 밖" = **강의 학습 범위 경계**(애플리케이션 제작은 강의가 다루지 않음), *비개발자 불가*가 아님. ADR-0008은 애플리케이션을 "결정성·비용 비교 끝점"으로만 규정(§2), "개발자가 만든다" 주장 없음 → **ADR 수정 불요**, docs 문구만 정정(결정성 축은 불변).
- **반영(`basics.md` 세형태)**: ① note 끝 칸 "개발자가 만드는 결정적 소프트웨어" → "결정적 코드 소프트웨어 … 본 교육 다루는 범위 밖" ② 표 '만드는 비용·누가' 애플리케이션 칸 "개발자가 코드 작성" → "설계·코드·테스트가 필요(엔지니어링 영역)" ③ 표 뒤 문단: 에이전트가 코드 작성을 거들어 문턱이 낮아짐을 인정하되, 안정적 제작엔 설계·테스트·유지보수가 들고 **본 교육은 거기까지 안 다룸**(초점=비개발자가 만드는 에이전트 스킬)로 재서술.
