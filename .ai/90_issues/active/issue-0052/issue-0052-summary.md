- audit 발견: 이 Task와 관련된 audit 발견사항 건수 ― 없으면 `0건` (`-` 금지)

한 발견이 여러 Task 산출물에 걸쳐도 가장 직접 수정된 주 Task 하나에만 귀속한다 ―
`audit 발견`·`보정 반영` 모두 그 주 Task에서 1회만 세고 관련된 다른 Task에는 세지 않는다.
Task 축에서도 이슈 단위 합계가 중복으로 부풀지 않게 하기 위함이다(아래 회차 축 중복 제외와 같은 취지).

1건으로 세고(중복 제외), 새 회차 값으로 덮어쓰지 않는다. 보정률 사후 집계의 분모·분자가 회차 반복으로 부풀지 않게 하기 위함이다.

수치 3종에 `-`를 쓰지 않는 이유: 아래 스니펫이 `[0-9]+`만 추출하므로 `-`인 Task는
합계에서 조용히 빠지고, 전부 `-`면 합계 자체가 빈 문자열이 된다. `-` 허용은 비수치 필드(`수행 모델`)에만 둔다.

수치 3종의 기본값은 주석이 아니라 리터럴 `0건`/`0회`로 둔다: 주석 placeholder는 렌더링 값이
비어 있는데도 집계기가 주석 안 숫자를 실제 값으로 오인하고, `미기록` 같은 형식 위반도 걸러지지 않는다.

보정률은 별도 필드로 두지 않고 `보정 반영 / audit 발견`으로 사후 집계한다.
아래 스니펫이 동작하도록 `- **<필드>**: <숫자><단위>` 표기를 지킨다 (줄 시작, 굵게, 콜론 뒤 숫자).

  # 이슈 하나의 보정률

  echo "보정률: ${fixed}/${found}"

  grep -E '^- \*\*(수행 모델|audit 발견|보정 반영|재시도)\*\*:' issue-0052-summary.md

- **audit 발견**: 0건

- **수행 내용 요약**: 구성안 17~31장을 16장 뒤에 이어 작성했다(+679행). 구성은 MCP 서버 divider 1장 + 본문 10장(`docs/connect/mcp-servers.md` 파생) + 연결 보안 3장(`docs/security-guide.md#external-connection` 파생) + 정리 1장이다. 덱 전체 제목 수는 77 → 92개, 파일은 3181행이 됐다. 31장 뒤에 `layout: end` 슬라이드를 두지 않았고(구성안 2절), 다음 슬라이드는 기존 1부 「실습」 섹션 divider다. `[D]` 게이트 4종(31장 전수 제목·순서 · 배치 · Slidev 빌드 · U+2014 0건) 전부 통과를 실행으로 확인했다.
- **특이 사항**: ADR-0010 결정 3-1의 두 갈래를 19·20장으로 나눠 유지했다. 19장은 「설정을 어디에 두나」(접속 주체를 정하는 갈래), 20장은 「서버가 어디에서 실행되나」(설정 위치와 독립)이며, 20장에서 두 조합에 A·B 라벨을 붙여 22장 mermaid에서 회수한다. ADR이 이 갈래를 뒤늦게 추가한 이유(원격/로컬 한 갈래로 누르면 사내망 케이스가 빠짐)를 20장 발표자 노트에 남겼다. 슬라이드 본문에 「축」이라는 말은 0건이고(검증 실행), 발표자 노트에서만 ADR 서술을 참조한다.
  mermaid 2장(21·22장)은 docs 원본의 노드·간선·색 지정을 그대로 가져왔다. 덱 mermaid가 `setup/mermaid.ts`에서 neutral(라이트) 고정이라 docs의 연한 파랑 style 지정이 그대로 산다. 22장에서만 노드 라벨의 「사내 데이터」 이탤릭 한 줄을 뺐다(슬라이드 폭에서 노드가 3행이 되면 그림이 눌림). scale은 21장 0.72, 22장 0.62로 잡았고 **둘 다 Task 6 viewport 점검 대상**이다.
  구성안의 병합 표시를 적용해 두 장을 묶었다. 26장은 docs 세 박스(열쇠 값 발급 · 열쇠 값을 대화창에 넣지 않기 · 「항상 허용」)를 「승인을 미리 좁히기 vs 승인을 나중에 열기」 갈래로 한 장에, 27장은 `#after-connect`·`#troubleshooting` 두 절을 「잘 될 때 / 안 될 때」로 한 장에 묶었다.
