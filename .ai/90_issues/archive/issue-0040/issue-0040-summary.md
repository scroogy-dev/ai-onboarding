### Task 1: 메시지 프레임 정합 검토 — ADR-0005 §3와의 관계 정리

- **결과**: 완료
- **수행 내용 요약**:
  - ADR-0005 §3 ("결정성/비결정성은 결과형으로 우회 전달") 재독. 현재 `docs/index.md` L145–186 "매번 시키기 vs 소프트웨어로 만들기" 박스가 이 원칙을 충실히 따르고 있음 — "매번 결과가 조금씩 다름"·"동일 품질로 반복 보장" 등 **결과형 표현**만 사용, "비결정"이라는 단어 자체는 본문에 부재.
  - Issue #40 요구사항을 ADR-0005 §3와 대조: "결정 vs 비결정 차이를 알려준다" + "기본적으로 비결정적이라는 점을 인지시킨다"는 **메커니즘 단어의 명시적 도입**을 요구 → §3 원칙과 정면 충돌.
  - ADR-0001 3단계 모델(챗봇 → 프롬프트 재활용 → 에이전트)과 Issue #40 비교 3종(1회성 프롬프트 / 에이전트 스킬 / 애플리케이션)의 차원 차이 확인:
    - ADR-0001 = **학습자의 활용 수준 사다리** (1단계→3단계로 올라감)
    - Issue #40 = **결과물의 형태·체계화 수준** (1회성 ↔ 스킬 ↔ 애플리케이션)
    - 두 분류는 부분 겹치지만 동일하지 않음. "애플리케이션"은 ADR-0001 3단계 바깥에 있는 **비교 기준** — 학습자가 "내가 만드는 스킬"의 위치를 두 끝점 사이에서 인지하게 하는 장치.
  - **처리 방향 결정: (B) 신규 ADR + ADR-0005 §3 후속 변경 노트**
    - 신규 ADR (가제): "결정성/비결정성 메커니즘의 명시적 가시화 — 비교표 형태로 도입". ADR-0005 §3의 기본 원칙(본문 결과형)은 유지하되, 비교표 1곳에 한해 메커니즘을 직접 명시.
    - ADR-0005 §3에는 후속 변경 노트 추가: "본문 기본은 여전히 결과형, 비교표 1곳만 메커니즘 명시"로 운용 변경.
    - ADR-0001은 본문 변경 없음. 단 신규 ADR에서 "Issue #40 3종은 ADR-0001 3단계와 다른 차원"임을 명시.
  - 신규 ADR 작성과 ADR-0005 후속 변경 노트는 Task 5에서 처리.
- **특이 사항**:
  - (C) 결과형으로만 비교표 구성 안 검토 → 이슈 본문 명령("차이를 알려준다", "비결정적이라는 점을 인지시킨다")과 직접 충돌하므로 기각.
  - (A) ADR-0005에 단순 후속 변경 노트만 추가 안 검토 → "§3 원칙 유지 + 비교표만 예외"라는 운용은 자체로 일관성이 약해, 결정을 신규 ADR로 격상하는 것이 정직.
  - 신규 ADR 작성 시점에서 ADR-0005 §3 노트와 짝으로 처리. 두 ADR이 모순되지 않도록 같은 PR에서 묶어 갱신.

- **수행 내용 요약**:

  - **메커니즘 단어 도입 위치는 2곳으로 한정**: ① 비교표 위 단정 박스 (이슈 명시 요구 "비결정적이라는 점을 인지시킨다"), ② 비교표 "결정성" 행. 다른 본문은 결과형 유지.
  - 비개발자 친화 톤 점검: "LLM", "샘플링", "temperature", "확률 분포" 등 메커니즘 깊이 단어 미사용. "결정/비결정"이라는 용어는 도입하되 결과형 표현이 받쳐주는 구조.
  - 본 교육 위치 지표: 표 헤더 `에이전트 스킬` 옆에 `(본 교육)` 표기, `애플리케이션` 옆에 `(소프트웨어)` 부연. 결론 문구에서 "에이전트 스킬은 두 끝점 사이"임을 명시 → ADR-0001 3단계 모델의 ②③단계가 이 위치에 매핑됨을 자연 인식.

#### 비교표 마크다운 초안

> **단정 박스 (표 직전 배치)**
>
> !!! warning "생성형 AI는 기본적으로 비결정적입니다"
>     동일한 지시를 입력해도 매번 답이 조금씩 다를 수 있습니다. AI를 어떤 **형태**로 활용하느냐에 따라 이 비결정성을 얼마나 통제할 수 있는지가 달라집니다.

> **도입 문구**
>
> AI를 활용하는 방식은 결과물의 형태에 따라 셋으로 나뉩니다. 같은 작업도 어떤 형태로 만드느냐에 따라 **결과의 일관성**과 **만드는 비용**이 크게 달라집니다.

| 축 | 1회성 프롬프트 | 에이전트 스킬 *(본 교육)* | 애플리케이션 *(소프트웨어)* |
|---|---|---|---|
| **무엇인가** | 챗봇에 그때그때 입력하는 한 번짜리 지시 | 자주 쓰는 프롬프트·절차를 재사용 가능한 형태로 묶어둔 자산 | 코드로 작성된 프로그램 |
| **결정성** | 비결정 | 비결정 *(내부가 LLM 호출)* | 결정 |
| **결과 일관성** | 매번 결과가 조금씩 다를 수 있음 | 동일한 형식·접근 보장 *(값은 다를 수 있음)* | 동일 입력 → 동일 출력 |
| **만드는 비용·누가** | 없음 — 누구나 즉시 | 낮음 — **비개발자도 직접 만듦** | 큼 — 개발자가 코드 작성 |
| **언제 적합한가** | 일회성·탐색·맥락이 매번 다른 작업 | 반복되는 동일 패턴 작업 | 대규모·다수 사용자·결정적 신뢰성이 핵심인 작업 |

> **결론 문구**
>
> 본 교육이 강조하는 **에이전트 스킬**은 두 끝점 사이에 있습니다. 비개발자가 만들 수 있는 비용이면서, 반복 작업의 일관성을 크게 끌어올립니다. 결정적 신뢰성이 핵심인 영역(공식 시스템·다수 사용자 대상)은 여전히 개발자가 만드는 **애플리케이션의 영역**입니다.

- **특이 사항**:
  - "결정성" 셀의 `비결정 (내부가 LLM 호출)` 부연은 학습자가 "스킬은 코드라서 결정적이지 않나?"라고 잘못 추론할 위험을 막는 안전장치. 메커니즘 깊이까지 가지 않고 한 문구로 닫음.
  - "만드는 비용·누가" 축에서 에이전트 스킬을 `비개발자도 직접 만듦`으로 명시 강조 — ADR-0005 핵심 메시지("비개발자도 소프트웨어를 만든다")와 정렬.
  - Task 3에서 삽입 위치 확정 시, 본 표가 기존 `docs/index.md` L145–186 "매번 시키기 vs 소프트웨어로 만들기" 박스와 시멘틱 중복 없는지 점검 — 두 자산은 다른 일을 한다(결정 룰 박스 = 2분기 가이드, 본 표 = 3종 위치 비교). 별도 자산으로 공존 가능하다 보지만, 배치 거리에 따라 흐름 자연스러움 차이가 있을 수 있음.
