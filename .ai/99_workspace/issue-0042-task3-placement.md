### 핵심 진단

1. **하네스 구성요소는 세 문서에 이미 다 깔려 있다** (Task 1 §0 발견). 그러나 *"이 조각들이 하나의 구도(모델+하네스)"* 라고 묶어 주는 자리가 **없다.** → Task 1·2의 멘탈모델이 들어갈 *빈 자리*가 분명히 존재.
2. **에이전트 정의의 깊이 차이** — intro §챗봇 vs 에이전트는 *사용 방식*("맡기기")까지만 정의하고, *"에이전트가 무엇으로 이뤄졌나"*(해부)는 비어 있다. 모델+하네스가 이 해부 자리를 채운다.
3. **멀티 에이전트 자율성 오해를 푸는 자리가 어디에도 없다** — 이슈 #42가 해소하려는 바로 그 오해. 신설 필요.
4. **basics.md §바이브/에이전틱 → §외부 컨텍스트 사이가 논리적으로 끊겨 있다** — §외부 컨텍스트(MCP 연결)가 *부모 개념 없이* 떠 있다. 그 사이에 모델+하네스를 넣으면 "외부 컨텍스트 = 하네스의 *연결하기* 한 부품"으로 자연 연결된다.

## 1. 배치 결정 — 집은 `basics.md`

**`에이전트 = 모델 + 하네스` 멘탈모델의 본가는 `basics.md`다.** 근거:

- basics는 *"기본 용어와 범위"* — 멘탈모델은 개념 프레이밍이고, 오해 해소는 *범위/경계* 콘텐츠라 톤이 맞다 (이미 `!!! warning 비결정성` 박스가 있어 warning 박스도 자연스럽다).
- 하네스를 이루는 두 인접 섹션(§바이브/에이전틱 = *만들기*의 배경, §외부 컨텍스트 = *연결하기* 한 부품)이 **바로 옆에 있다.**
- intro는 *"빠르게 훑고 넘어가도 됨"* 페이지 — 이슈의 핵심 메시지(오해 해소)를 *건너뛸 수 있는 페이지*에 묻으면 안 된다.

**intro·index는 본가가 아니라 연결고리만 추가** (§3 교차링크).

### 새 섹션 위치 (basics.md 내부 순서) — Task 5 피드백 반영(2026-05-31)

```
## AI 활용의 세 형태
## 마크다운
## 에이전트 = 모델 + 하네스        ← 신설
## 외부 컨텍스트
```

> **변경**: 원안은 §바이브 코딩 ↔ §외부 컨텍스트 사이였으나, Task 5에서 사용자가 **`## 바이브 코딩과 에이전틱 엔지니어링` 섹션 자체를 제거**하기로 결정(비개발자에게 이 구분이 실력 향상으로 이어지지 않음 → 개발자 패러다임 격상 회피). 모델+하네스 신설 섹션은 intro §챗봇 vs 에이전트 정의에서 직접 이어지므로 바이브 섹션 없이도 흐름이 성립한다. §외부 컨텍스트는 여전히 "하네스의 *연결하기* 한 조각"으로 흡수.
>
> docs 내 `#vibe-vs-agentic` 역참조는 없어 깨진 링크 없음. `slides/slides.md` 해당 슬라이드 1장은 잔존 → 이슈 #42 범위 밖(후행 정리).

## 2. 신설 섹션 구조 — `## 에이전트 = 모델 + 하네스 { #model-harness }`

비개발자 과부하 방지를 위해 **짧게**. 「목록이 짧다는 것 자체가 메시지」(Task 2) 원칙 유지. 4블록:

| 블록 | 내용 | 출처 | 형태 |
|------|------|------|------|
| **(1) 한 줄 멘탈모델 + 정의** | `에이전트 = 모델(생각하는 머리) + 하네스(사람이 짜 둔 틀)`. 모델=똑똑하지만 틀릴 수 있고 매번 다를 수 있음 / 하네스=둘러싼 작업 구조 | Task 1 §1·§2 | 본문 + 짧은 대비표 |
| **(2) 하네스 = "내가 세팅하는 것들"** | 출처 셋(회사 제품·모델 / 외부 서비스=연결만 / 내 설정) → 내 몫은 *만들기*(지시·자료·순서·검토)+*연결하기*. 회사 몫도 자율 아님 → **"마법 아님"** | Task 1 §2 + Task 2 §2·§3·§4 | `!!! info` 또는 2열 grid |
| **(3) 흔한 오해 박스** | "에이전트끼리 알아서 회의하면 좋은 결론" → 3박자(하네스는 마법 아님 / 모델은 틀릴 수 있음 / 좋은 결론은 「알아서」 안 남). 메타 원칙 ③ 링크 | Task 1 §3 | `!!! warning` (단정형, 외부 인용 없음) |
| **(4) 멀티 에이전트 긍정 사례** | 분야별 기준 검수(역할 분업 + 명시적 기준표 + 사람 검토). "가치는 자율이 아니라 설계" | Task 1 §3 뒤집으면 | **분량 결정 필요 ▼** |

### 프롬프트↔하네스 경계 (Task 1 §2)

별도 블록으로 빼지 않고, **(1) 정의 안에 한 줄**로 흡수 — *"모델에게 건네는 말 한마디(프롬프트)가 아니라 그 둘레의 구조"*. basics §세 형태의 `1회성 프롬프트 vs 에이전트 스킬` 경계와 같은 선이므로 그쪽으로 링크.

## 3. 교차링크 — intro·index는 연결고리만

신설 섹션이 *이미 있는 자산*을 가리키게 해서 중복 서술을 피한다 (Task 1·2가 반복 금지로 누차 강조).

| 신설 섹션에서 → | 가리키는 기존 자산 | 의미 |
|----------------|-------------------|------|
| (1) "같은 모델, 다른 하네스" | intro [§기능 비교표](intro.md#claude-comparison) | 세 제품이 같은 모델·다른 하네스 |
| (2) "회사가 만든 하네스 부품" | intro [§Cowork 보호 모델](intro.md#claude-cowork) | 격리 VM·송신 정책 = 회사가 만든 하네스 실물 |
| (2) "연결하기" | basics [§외부 컨텍스트](#external-context) | MCP 연결 = 하네스 연결 부품 |
| (2) "만들기" 항목들 | index [메타 원칙 ①③④](index.md#meta-principles) | 만들기 = 이미 배운 메타 원칙 |
| (3) 오해 박스 결론 | index [메타 원칙 ③](index.md#meta-principles) | 검토 의무는 협상 대상 아님 |
| (1) 프롬프트 경계 | basics [§세 형태](#three-forms) | 1회성 프롬프트 vs 스킬 경계 |

**intro §챗봇 vs 에이전트에 역링크 1줄(선택)**: *"에이전트가 무엇으로 이뤄졌는지는 [모델 + 하네스](basics.md#model-harness)에서"* — 해부 자리로 내려보내는 다리. (index/intro 본문 신규 서술은 없음 — 링크만.)
