## 0. 핵심 발견 — 강의는 이미 하네스를 가르치고 있다

이 강의는 "하네스"라는 이름만 안 붙였을 뿐, **그 구성요소를 이미 다 다룬다.**

- `docs/basics.md` §바이브 코딩·에이전틱 엔지니어링 → *"입력에 줄 컨텍스트와 자산(규칙·템플릿·검토 자리)을 의도적으로 설계"* = 하네스 그 자체
- `docs/index.md` 메타 원칙 ①(계획/실행 분리)·③(결과물 검토 의무)·④(컨텍스트 관리) = 비개발자가 실제로 다루는 하네스 구성요소
- `docs/intro.md` §챗봇 vs 에이전트의 "맡기기" = 에이전트 정의의 발판

→ Task 1은 **새 개념 도입이 아니라**, 흩어진 조각을 `모델 + 하네스` 한 구도로 묶고 그 위에 오해 해소 메시지를 얹는 일이다.

## 1. 한 줄 멘탈모델

> **에이전트 = 모델(생각하는 머리) + 하네스(그 머리를 둘러싼 작업 구조)**

---

## 2. 비개발자 한 줄 정의

| 구분 | 한 줄 정의 | 기존 강의 연결 |
|------|-----------|---------------|
| **에이전트** | AI가 직접 파일을 열고 일하고, 사람은 *목표만 주고 결과를 검토*하는 사용 방식 | intro §챗봇 vs 에이전트("맡기기"), ADR-0001 3단계 |
| **모델** | 생각하는 머리. 똑똑하지만 *틀릴 수 있고*, *매번 답이 조금씩 다를 수 있는* 부분. 만드는 회사는 여럿 — **Anthropic(Claude)·OpenAI(ChatGPT)·Google(Gemini)** 등, 그 외 공개된 **오픈소스 모델**도 있음. *본 강의 실습은 Claude*(라인업: Opus·Sonnet·Haiku) | intro §products·§모델 비교, ADR-0001 |
| **하네스** | 그 머리를 **둘러싼 작업 구조** — 어떤 도구·자료를 쓸지(스킬·컨텍스트), 어떤 순서로 일할지(계획), 결과를 어디서 검토할지(검토 자리). *모델에게 건네는 말(프롬프트) 자체가 아니라 그 둘레의 장치* | basics §에이전틱 엔지니어링, 메타 원칙 ①③④ |

### 모델 ↔ 하네스 대비

| 축 | 모델 | 하네스 |
|----|------|--------|
| **무엇** | 생각하는 머리 | 머리를 둘러싼 작업 구조 |
| **누가 만드나** | **여러 제공자** — Anthropic·OpenAI·Google 등(+오픈소스), 내가 고르기만 (본 강의는 Claude) | **여러 곳** — 제품·모델은 회사가, 외부 도구·자료(GitHub·Slack 등)는 서드파티/사내 인프라가, 내 설정(스킬·순서·검토)은 내가. 대부분 *만드는 게 아니라 골라·연결·설정해 조립* |
| **성격** | 똑똑하지만 틀릴 수 있고, 매번 조금씩 다름 | 한 번 정해 두면 그대로 반복 |
| **예** | "이 회의록 요약해"를 알아듣고 써내는 능력 | 어떤 스킬·자료·순서로 시킬지, 그리고 결과를 검토하는 자리 |

> 이 대비는 ADR-0005 결정 룰의 결과형(모델=매번 다름 / 사람이 짠 구조=반복 보장)과 결을 같이한다 — 메커니즘 단어 없이 자연 정합.

### 하네스는 내가 다 만드는 게 아니다 — 대부분 "조립"이다

"누가 만드나"가 오해 포인트다. 하네스를 *내가 다 만든다*고 하면 틀리고(대부분 이미 있는 걸 조립·연결한다), *제품이 알아서 한다*고 하면 그게 자율성 오해다. 하네스를 이루는 것은 **출처가 셋**이다.

- **회사가 만든 것 — 에이전트 제품·모델** — 에이전트 제품 *자체*(파일 여는 손, 도구를 반복 호출하는 루프, 격리 VM·권한·송신 정책)와 그 안의 모델. 제품(Cowork·Code)은 도구 회사가, 모델은 여러 제공자(Anthropic·OpenAI·Google 등, +오픈소스) 중 하나 — 본 강의는 둘 다 Anthropic(Claude). *"알아서 파일 열고 명령 실행"처럼 보이는 동작이 바로 이것* — 모델이 스스로 자율적인 게 아니라 **회사가 만든 하네스가 모델을 굴린 것**.
- **이미 있는 외부 서비스·사내 인프라 — 내가 연결만 함** — MCP 등으로 잇는 GitHub·Slack·Jira·Confluence 같은 도구·자료원. 서드파티 서비스이거나 사내에 이미 설치된 인프라다. 나는 **연결(로그인·승인)** 할 뿐, 그 서비스를 직접 구축하는 경우는 거의 없다.
- **내가 만드는·정하는 것 — 내 설정** — 어떤 스킬을 쓸지, 어떤 폴더·자료를 붙일지, 어떤 순서로 시킬지, 결과를 어디서 검토할지. 셋 중 *내 손으로 만드는 부분*이지만, 전체에서 보면 얇다.

> **정리** — 하네스 = 이미 있는 부품(회사 제품·외부 서비스·사내 인프라)을 **고르고·연결하고·설정하고·검토해 조립한 것.** 내가 밑바닥부터 만드는 건 적고, 어느 조각도 "스스로 똑똑한" 게 아니다 → 결과 품질은 *조립을 잘했는지 + 사람이 검토했는지*에서 온다.

> **같은 모델, 다른 하네스** — `claude.ai`(스스로 파일·명령 실행 없음 = 챗봇) / `Cowork`(연결 폴더·격리 VM = 에이전트) / `Code`(전체 파일·터미널 = 에이전트). 세 제품은 같은 모델 라인업(Opus·Sonnet·Haiku)을 공유하고 *회사가 만든 하네스*가 다를 뿐 — intro 기능 비교표가 그 차이표, §Cowork 보호 모델의 격리 VM·송신 정책이 "회사가 만든 하네스 부품".

### "프롬프트도 하네스인가?" — 경계

"둘러싼 구조"라고만 하면 *1회성 프롬프트도 틀 아닌가?* 라는 혼동이 생긴다. 경계를 명시한다.

- **프롬프트(1회성 지시)** = 모델에게 건네는 **말 한마디(입력)**. 그 자체는 하네스가 아니다 — 머리에게 질문을 하나 던지는 것.
- **하네스** = 그 모델이 *에이전트로 일하게* **둘러싼 구조**(도구·자료 접근, 순서, 검토 자리).
- 경계선은 **"한 번 던지고 끝" vs "둘러싸 상시로 둠"**: 같은 지시를 반복하려고 **저장해 자산으로 묶으면(스킬)** 그때부터 하네스의 *부품*이 된다. ← 강의의 `1회성 프롬프트 vs 에이전트 스킬`(basics 세 형태)과 같은 경계.

## 3. 핵심 오해와 해소 (단정적 원칙형)

**오해**: *"하네스를 짜서 에이전트 여럿을 띄우면, 걔네끼리 알아서 회의하고 조사해서 좋은 결론이 나온다."*

**해소 3박자**

1. **하네스는 마법 지능이 아니라 누군가 만들어 둔 것을 조립한 구조다.** 제품(Cowork·Code)은 회사가, 외부 도구·자료는 이미 있는 서비스에 *연결*만, 내 설정(스킬·순서)만 내가 — *알아서 파일 열고 명령 실행하는 것처럼 보여도, 회사가 만든 하네스가 모델을 굴린 것*이지 모델이 스스로 자율적인 게 아니다. 멀티 에이전트도 그 구조의 *한 기법*일 뿐.
2. **모델은 똑똑해도 틀릴 수 있다.** 여럿이 모여 회의해도, 잘못된 전제 위에서는 **그럴듯하게 함께 틀린 결론**을 낼 수 있다.
3. **좋은 결론은 「알아서」 나오지 않는다.** *틀을 잘 짠 사람 + 결과를 검토한 사람*이 만든다.

> 핵심은 "멀티 에이전트가 쓸모없다"가 아니라, **"사람 없이 알아서"** 부분이 오해라는 것. 정직하게: 멀티 에이전트는 결과를 끌어올리는 한 기법이지만, 그 품질도 사람이 짠 구조와 사람의 검토에서 온다.

### docs용 "흔한 오해" 박스 초안 (단정형 · 외부 인용 없음)

```markdown
!!! warning "흔한 오해 — 「에이전트끼리 알아서 회의하면 좋은 결론이 나온다」"
    AI 여러 개를 띄워 서로 회의시키면, 사람 손을 떠나 알아서 조사하고
    정답을 내놓을 거라 기대하기 쉽습니다. 그렇지 않습니다.

    - **틀(하네스)은 마법이 아닙니다.** 무엇을 시킬지·어떤 자료를 줄지·어떤
      순서로 할지는 **누군가 설계해 둔 것**입니다 — 제품을 만든 회사, 그리고
      그 위에 설정한 나.
    - **모델은 똑똑해도 틀릴 수 있습니다.** 여러 AI가 모여 회의해도, 잘못된
      전제 위에서는 **그럴듯하게 함께 틀린 결론**을 낼 수 있습니다.
    - **좋은 결론은 「알아서」 나오지 않습니다.** 틀을 잘 짠 사람과 결과를
      검토한 사람이 만듭니다.

    그래서 [AI 결과물 검토·이해 의무](index.md#meta-principles)는
    협상 대상이 아닙니다.
```

### 뒤집으면 — 멀티 에이전트가 "제대로" 쓸모있는 순간 (분야별 기준 검수)

"알아서 회의"가 오해라고 해서 멀티 에이전트가 쓸모없다는 건 아니다. *사람이 역할과 기준을 잘 설계하면* 분명히 유용하다. 대표 사례 — **하나의 기획안을 분야별 검수자가 각자의 기준표로 점검**:

| 검수자(역할) | 평가 기준(체크리스트) 예 |
|---|---|
| **법무** | 개인정보 수집·동의 절차 명시? 외부 콘텐츠 저작권·라이선스 확인? 경품·광고 고지 문구? 과장 표현 소지? |
| **재무** | 예산 항목·총액 산정 근거? 비용 회수(ROI) 가정? 숨은 비용(수수료·세금) 누락? 초과 시 처리? |
| **보안** | 수집 데이터 저장·접근 권한? 외부 연동 시 송신 범위? 민감정보 마스킹? 사고 시 대응 경로? |

흐름: 각 검수자가 *자기 기준표*로 기획안을 훑어 **항목별 통과/지적 + 개선 제안**을 내고 → **사람(기획자)이 취합·판단·반영**.

**가치를 만드는 건 '자율'이 아니라 두 가지다.**

1. **잘 나눈 역할** — 한 모델이 다 보는 것보다, 서로 다른 관점으로 나눠 보면 놓치는 게 준다.
2. **명시적 평가 기준** — *기준이 있어야 판단·개선이 쉽다.* "음, 괜찮네요" 같은 모호한 평 대신 *항목별 통과/지적*으로 떨어지니 무엇을 고칠지 분명해진다. (이 기준표 = [메타 원칙 ① 완료의 정의·체크리스트](index.md#meta-principles)의 분야별 버전)

**그래도 사람 손은 빠지지 않는다.**

- 검수자도 *모델이라 틀릴 수 있다* → 지적을 그대로 믿지 말고 사람이 최종 검토(메타 원칙 ③).
- 상충하는 지적(법무 "이 문구 빼라" ↔ 마케팅 "효과상 넣어야")은 *사람이 결정*한다 — 에이전트끼리 합의를 강제하지 않는다.
- 기준표 자체의 품질이 결과를 좌우 → *기준도 사람이 만들고 다듬는다.*

> **눈높이 주의** — 이건 *개념 사례*다. 당장 진짜 멀티 에이전트를 구성하라는 게 아니라, 핵심(역할 나누기 + 기준표 + 사람 검토)은 **단일 에이전트로도** "각 분야 기준표로 차례차례 점검"해 대부분 얻을 수 있다. (학생·일반인 트랙이면 '법무·재무·보안'을 '구성·근거·맞춤법' 같은 기준으로 치환.) 멀티 에이전트는 이 그림을 더 또렷이 보여줄 뿐.

## 4. 정합성 확인

| 기준 | 확인 결과 |
|------|----------|
| **ADR-0001** (3단계 모델) | `모델+하네스`는 *"에이전트가 무엇으로 이뤄졌나"*(해부) 축으로, *학습자 수준 사다리*(3단계) 축과 **차원이 다름**. ADR-0008이 3종 분류를 별 차원으로 둔 것과 같은 처리 — 강제 매핑하지 않는다. ✅ 충돌 없음 |
| **ADR-0005 §3 / ADR-0008** | 모델 설명을 결과형("틀릴 수 있다 / 매번 조금 다를 수 있다")으로 유지하고, **'비결정' 메커니즘 단어를 새 자리에 도입하지 않음**(그 단어는 basics 세 형태 비교표 1곳에 한정). ✅ 운용 범위 유지 |
| **메타 원칙 ③** (검토 의무) | 오해 해소 메시지가 *안착하는 자리*. ①(계획/실행 분리)·④(컨텍스트 관리)는 하네스 구성요소로 자연 연결. ✅ 기존 자산 재사용 |
| **basics §에이전틱 엔지니어링** | 내가 *만드는·정하는* 부분은 '내가 세팅하는 작은 것들'까지만 (에이전틱 엔지니어링 본격 설계는 비개발자에게 요구 안 함). 정식 범위 설계는 Task 2. ✅ 정합 |
| **intro 기능 비교표 · §Cowork 보호 모델** | 세 제품(claude.ai/Cowork/Code)이 *같은 모델·다른 하네스*임을 보여주는 표 = "회사가 만든 하네스" 근거. 격리 VM·연결 폴더·송신 정책 = 회사가 만든 하네스 부품. ✅ 기존 자산이 출처 구분을 뒷받침 |
